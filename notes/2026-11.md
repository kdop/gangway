## 2026-11-19 Design overhaul
*tags: design, blueprint, plan, gate, controller, tailscale, tsnet, go, session-key, folder-grants, safe-commands*

- Kostas restated the idea: Gangway is just-in-time approval of the commands an AI may run on a host. Not a product. The reason is that SSH gives no say over the commands.
- Kostas changed the shape: a controller on Tailscale replaces the public rest-api. The AI calls the controller's API and does not have to be on Tailscale. The session key lives 30 minutes. The web page and Google login are out of the first version.
- Kostas left the product and planning docs to Claude. `blueprint.md` was rewritten, `plan.md` and `README.md` were added. The first draft of the blueprint is in git at `d963186`.
- Calls Claude made that Kostas has not confirmed line by line: the gate lives in the cli-tool, approval in the host terminal, the cli-tool makes the key, the key is tied to the first AI, no root. They are marked in `CLAUDE.md`.
- Kostas added folder grants: the cli-tool names the folders the AI may read, at a later stage, not in the first version. Claude's limit: hard for file reads only, no sandbox for commands yet.
- Kostas added a choice to approve all safe, read-only commands, also at a later stage. Claude's limits: fixed list, no shell, nothing that prints file contents until folder grants exist.
- Kostas agreed to Go for the cli-tool. Claude's calls on top: Tailscale built in with `tsnet`, an ephemeral tagged auth key, the controller in Go too. `tsnet` and auth key facts checked against the Tailscale docs today.
- Kostas said the controller is a web app, a REST API with a dashboard, and left the stack to Claude (not keen on Django). Claude's call: Go, server-made pages with htmx, dashboard on the Tailscale side only.
- Kostas: where the controller listens is a setting (default localhost, can be Tailscale), not a design question. "Always allow" moves to the second stage; the first version asks `y`/`n` every time.
- Kostas: time and size limits on a command, not strict, with a "go on or stop" question past a limit. `login` once, key in a file in the home folder, never given to the AI. Dots on start, then the session key.
- Kostas: Linux hosts only. No open design questions are left; step 1 of `plan.md` can start.
- Kostas asked where the yes/no lives; accepted the cli-tool. Storage settled: plain files on the host, sessions in memory only, no database yet.
- Dropped: signing commands end to end. With the gate on the host, a bad controller can only ask.

## 2026-11-20 Design review: talked about, not yet in the docs
*tags: review, mvp, monorepo, requirements, tests, admin-settings, etc, read-only, folder-grants, sudo, diff, backups, python, open-questions*

- MVP scope agreed: steps 1, 3 and 10 of `plan.md`, on one machine, no Tailscale yet. Not started. Kostas wants to talk about it again before it starts.
- Tying the session key to the first caller stays out of the MVP. Kostas: it would also stop sharing a session. Kostas later the same day: the key belongs to the first AI, for now. It is step 4, after the MVP.
- Kostas: one repo for everything. Claude's layout, not confirmed: one Go module, `cmd/gangway/`, `cmd/gangway-controller/`, `internal/` for the shared message types, `skill/`.
- Requirements, method agreed, nothing written: a `requirements.md` with one testable "must" sentence per hard requirement, each with an ID that is never reused (`GATE`, `SES`, `KEY`, `PAIR`, `CTL`, `LOG`). Each Go test carries the ID in its name. A Go test lists IDs with no test. Each plan step names the IDs it delivers. Kostas's first example of a hard requirement: sessions are never resumed.
- Admin settings, Kostas agreed in talk: three layers that only narrow each other. `/etc/gangway/` owned by root (the folders that may ever be granted, the maximum session length), then `~/.config/gangway/`, then start options. Reason: an approved command runs as the plain user and could rewrite the user's own settings. This would answer the open question in the blueprint on where the maximum is set.
- Kostas wants to pass paths quickly at start, for example `gangway /var/log ~/app/config.yml`. He calls this the whole point of grants.
- Read-only mode, idea from Kostas: commands on a built-in read-only list run with no prompt and are shown; anything else gets the normal prompt, so the AI can still fix what it finds. A strict form that refuses everything off the list could be a start option.
- Kostas raised running the whole cli-tool with sudo for read-only mode. Claude pushed back: as root, a read-only command reads every secret on the host. Kostas: forget sudo and read-only mode for the MVP. Narrower ways named: a group that may read the logs, or a sudo rule for single commands.
- Dropped by Kostas for now: showing file changes as a diff. Claude's view on backups of touched files: not possible for plain commands, since the cli-tool cannot know what a command touches.
- Commands run with no terminal and no keyboard. Named in talk, not in the docs: set `PAGER=cat` and `TERM=dumb`, and let the skill teach plain forms such as `top -b -n 1`.
- Kostas is tired of Python. Nothing in the product uses it. Waiting for his word: change "Prefer plain parametrized pytest" in `.claude/rules/coding.md` to Go table tests.
- Settled the same day: when the session time runs out, a running command is not killed. Kostas agreed "for now" and said not killing can be exploited. The rule is in `blueprint.md` and `CLAUDE.md`.
- Kostas likes the GitHub description as it is ("Connect AI to any host, with guardrails built in."). Closed.
